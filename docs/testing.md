# Testing

A test is worth keeping if it catches a fault. So the backend's suite is kept small, and its strength is measured by the faults it catches, not by how many tests pass.

## Rules for every test

1. A test earns its place by catching a plausible fault that no other test catches, or by protecting a requirement where failure is serious: security, privacy (POPIA) or data loss. Otherwise it goes.
2. Expected values come from an independent source: the handbook, the printed transcript, my report, a hand calculation shown in a comment, or an independent oracle. Never paste in what the code returned.
3. Test boundaries on both sides, for example 5 and 6 plans, and meetings that touch as well as overlap.
4. Test each rule once, at the lowest level that can see it. A refusal the transcript reader raises is tested in the reader's tests, and the API tests check only that one reaches the client as its problem code.
5. Guards (signed out, outside UCT, staff, setup unfinished, questionnaire pending and another student's data) are checked once, in a sweep over every route the app serves, in `backend/tests/unit/shared/api/test_guards.py`. A new route that forgets a guard fails it automatically.
6. No count snapshots of seed data unless the number is a stated requirement. The seed's own counts are checked once, in the seed tests.
7. Every workaround, cut or known limitation goes in [shortfalls.md](shortfalls.md) as it's found.

## Acceptance tests

ATP-1 asks how well ingestion reads print, and whether anything wrong gets into SAGE without a person seeing it. Its label sheets, in `tests/acceptance/atp1/labels/`, were filled from print and committed before any run. Its harness compares SAGE's readers, grammar, drafts and approved years with them, field by field, and its report gives each measure with a 95% Wilson interval, with and without the labeller's judgement calls. [The harness's README](../tests/acceptance/atp1/README.md) says what it compares and how to read the report.

- `make atp1` runs it from the held-out drafts its first run cached, so it calls no model and needs no key. A rerun reproduces the report byte for byte.
- Those drafts were made once, with Claude Haiku 5.5, and the harness keeps no way to draft again: a new draft would be a retest.
- The harness's own tests, in `tests/acceptance/atp1/test_scoring.py`, check its scoring with values worked out by hand. `make test` collects them, so CI runs them. None reads a source or calls a model.
- `tests/acceptance/atp1/results/` keeps the first result. A fault it finds is fixed on its own branch, and the retest goes beside the first result, never over it.

## The dependency check

`make lint`, which `make check` and CI run, also runs import-linter's `lint-imports`. It reads every import in `backend/src/sage` without running the code, and checks the seven contracts in `backend/pyproject.toml` that hold [the backend's dependency rule](architecture.md#backend-dependency-rule). Each contract was broken once by hand to see it fail: shared code importing a feature, one feature importing another, a feature importing the engine's stand-in, a feature importing Supabase's SDK, the `sage` command importing Anthropic's, the plan generator importing clingo, and the advisor importing OpenAI's SDK or the engine. An exception a contract lists that no import still uses fails the check too, so the list can't go stale.

### UI checks

`make check-ui` runs Playwright against the local stack: local Supabase, the backend (`make dev` in `~/SAGE`) and this worktree's frontend on `PORT`, 3000 by default, which Playwright starts if it isn't running. If Supabase or the backend isn't running, it stops with one plain line saying which. The first run downloads Playwright's Chromium.

CI never runs it. It needs that stack, and screenshots differ between operating systems, so the parity images are compared by eye on my Mac. CI still type-checks and lints every spec and helper through `make check`.

- **Projects.** Light and dark, at 1280 by 820. A setup project signs Mbali in once per run with `make sign-in`'s link, allowing 90 s, as the command alone took 27 s on 21 October, and keeps her session in the git-ignored `frontend/e2e/.auth/`.
- **Made-up visitors.** Staff, an account from outside UCT and a student who hasn't finished setup are Mbali's session with a made-up answer from `GET /v1/me`, built from `api-types.ts`. So no check resets a real account, as every worktree runs these checks against one local database.
- **Helpers**, in `frontend/e2e/`:
  - `axe.ts` runs axe-core with the audit's tags: wcag2a, wcag2aa, wcag21a, wcag21aa and wcag22aa. The bar is zero violations.
  - `keyboard.ts` tabs through a page and checks that every stop shows the focus ring. It returns the stops in order.
  - `parity.ts` drives a prototype to a state through its own controls and writes it beside React.
  - `visitors.ts` holds the made-up visitors and the `freshStudent` fixture.
  - `settled.ts` waits until a page's animations have finished, in a prototype or in React.
- **Specs.** They end `.spec.ts` and sit in feature folders beside the Vitest tests, which end `.test.ts`, so neither runner loads the other's files. `src/app/routes.spec.ts` checks every page in the route table, as its visitor, with axe and the keyboard walk, `/plan` where it lands, at her first plan's own address.
- **Parity images.** Each feature keeps its cases in its own folder. The images land in `frontend/parity/<feature>/<case>-<theme>.png`, with `-hover` for the hover state. Where a prototype has no dark design, the dark image shows React alone. Onboarding is light only, so its cases run in light alone.

## How strong the tests are

| Command | What it reports | Time |
| --- | --- | --- |
| `make test` | The unit tests, then each file's lines that no unit test runs | 2 minutes |
| `make mutation` | The share of mutants the unit tests catch, written to `backend/mutation-score.txt` | 20 minutes |
| `make planted-faults` | Which of the 33 planted faults the unit tests catch, and the test that caught each: the 24 from my test review, two in the review and approval the thesis rests on, four in the plan encoding, which mutmut can't change, and three in the advisor's guardrails | 18 minutes |

Line coverage counts the lines that ran during the tests, not whether anything checked what they did, so it overstates. Mutation testing checks the checking. mutmut makes 8,321 copies of the code in `features/`, `shared/`, `ingestion/`, `engine/` and `advisor/`, each with one small change, such as `<` to `<=` or `5` to `6`. It runs the unit tests against each copy and counts the copies that make a test fail. A copy that makes the tests time out counts as caught. The 33 planted faults are plausible bugs chosen by hand, while mutmut makes every small change it can, most of them easy to catch, so its score runs higher.

The score leaves out the integration tests, code outside functions (such as the transcript reader's patterns), the adapters to outside services (the storage adapters, where student isolation is enforced, their in-memory fakes, Claude's drafter and OpenAI's client), and the entry points, `main.py`, `cli.py` and `config.py`.
